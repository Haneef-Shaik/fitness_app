## Findings

**M1 · Medium · carried from 0405Z, narrowed by SF-7, still open (it now blocks as a missing live check, not as a code defect)**
- **Location:** `mb1-replay-live.mjs:136-141` (`sharedBinding`), `mb1-replay-shared.mjs:77-84` (`stagedRoute`).
- **Defect:** the two checks never meet:
  - The binding check proves that Docker publishes the container the snapshots read at 55322.
  - The route proof proves that whatever answers at 127.0.0.1:55322 has exactly the 15 base migrations and not the candidate.
  
  Neither proves that these are the same Postgres. sf7.md §7 says this too.
- **Failure scenario:** a second listener on the host's 127.0.0.1:55322 (a tunnel, a port-forward, a second Docker runtime) sits in front of another stack built from this repo's 15 migrations. The route proof passes, `migration up` writes there, and only the after-apply snapshot STOPs, after the write.
- **Not reachable today:**
  - §6 is not authorized.
  - `sharedApplyNeeds` still lists five missing proofs.
  - A `0.0.0.0` plus `::` pair refuses every 55321 command.
- **Fix:** the live read also captures which process listens on host ports 55321 and 55322. A pure rule then requires that Docker's own process is the only listener. Close M1 after that.

**L1 · Low · new: nothing pins which Docker daemon the binding check reads**
- **Location:** `mb1-replay-exec.mjs:12` passes `DOCKER_HOST`, `DOCKER_CONTEXT` and `DOCKER_CONFIG` to every child, and `HOME` brings in `~/.docker`'s current context. The inspect call is at `mb1-replay-live.mjs:137`.
- **Defect:** the binding check, the start-time fingerprint and the `docker exec` snapshots all go to whichever daemon the environment selects. `migration up` and the route proof always dial this machine's loopback. sf7.md §7 names the shadowing-socket case but not this one.
- **Failure scenario:** the shell has `DOCKER_HOST=ssh://…`, or a context pointing at a second VM runtime. Every Docker read then describes that daemon's stack, while TCP reaches the local listener. This is M1's scenario by another route. I believe the CLI reports 127.0.0.1 for hosts that aren't `tcp://`, so `loopbackDb` would pass, but that is unverified.
- **Fix (pure):** for `shared: true` commands, refuse any `DOCKER_HOST` that isn't `unix://`. Check the scheme only and never print the value. Add fixtures for `tcp`, `ssh` and empty values. The live read records the context's endpoint.

**L2 · Low · new: snapshots read the container by name, not by the ID the binding proved**
- **Location:**
  - `mb1-replay-live.mjs:127` returns the name `SHARED.container`;
  - `mb1-replay-sql.mjs:21` runs `docker exec … <name>`;
  - `mb1-replay-shared.mjs:20-22` and `:162` use it;
  - neither inspect sets `--type container` (`mb1-replay-binding.mjs:28`, `mb1-replay-live.mjs:143`).
- **Defect:** the ID check brackets only shared-apply's fresh snapshot. `shared-snapshot` and the `55321-after` snapshot run after the last binding read, and `docker exec` resolves the name again. Without `--type container`, a missing container falls through to the same-named data volume, which I recall the CLI names `supabase_db_<project>`. That fails closed today, but only through template or ID errors, not by design.
- **Failure scenario:** another lane restarts the shared stack while `shared-snapshot before` runs, so the reference snapshot comes from a new container. The next command's start-time pin does catch it, so this is defence in depth.
- **Fix (pure):** `bindingProblems` returns the proven IDs, `sharedRunning` returns the database container's ID, and `readOnlyPsql` runs `docker exec` on that ID. Add `--type container` to both inspects. Test: a container replaced between the binding read and the exec refuses (for a snapshot) or STOPs (after `migration up`).

**L3 · Low · new: the route proof's exit check is only tested with empty output**
- **Location:** `mb1-replay-shared.mjs:79`; the test cases at `mb1-replay-sf7.test.mjs:79-80`; R-exit in sf7.md §4, killed "by message only".
- **Defect:** both failure cases print no stdout, and `routeProof` refuses empty output anyway. No test makes the CLI print a valid table and then exit non-zero.
- **Failure scenario:** a later refactor drops `:79`. The CLI prints all 16 rows and then exits 1. The proof passes, the attempt is recorded, and all 296 tests stay green.
- **Fix:** add a case `{ status: 1, stdout: <valid 15-remote table>, stderr: 'Error: …' }` that must refuse with no attempt recorded. Then re-run R-exit and show a real kill.

**L4 · Low · new: the STOP after `migration up` tells you to run a read that the guards will refuse**
- **Location:** the STOP text at `mb1-replay-shared.mjs:150` (also `mb1-replay-order.mjs:95`); the refusals come from `mb1-replay.mjs:134` (the start-time pin) and `mb1-replay-live.mjs:125` (the binding).
- **Defect:** every binding change SF-7 STOPs on (a new ID, a moved port) means the container was recreated, so its start time changed. A later `shared-snapshot after` is then refused before any SQL.
- **Failure scenario:** during an incident the coordinator follows the STOP's advice and gets a refusal. There is no written path outside the runner (that is SF-2).
- **Fix:** correct the STOP text, and define the manual read-only path in SF-2.

**Informational**
- **I1, widening for IPv6:** when the live read decides it, accept `::` only beside an IPv4 entry at the same port, because `migration up` dials IPv4. Never accept `::` alone. Keep `HostIp: ""` refused until it has been seen.
- **I2, the L1 scan:** `mb1-replay-scope.test.mjs:18,34-35` misses computed specifiers and ones with a query suffix, such as ``import(`./mb1-replay-${x}.mjs`)``. It guards against accidents, not deliberate evasion, which is acceptable.
