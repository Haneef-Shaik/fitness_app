## Findings, most severe first

### H1. The workflow guard only runs inside the job it guards, so skipping that job skips the guard
- **Severity:** High
- **Location:** `.github/workflows/backend-ci.yml:40-41` (the guard is step 4 of `jobs.backend`); `scripts/ci/workflow-guard.mjs:24`; `scripts/ci/workflow-guard.test.mjs:96-100`; `docs/plan/runs/PL-1/handoff.md:70`, `:189-192`
- **Defect:** When a job is skipped by an `if:`, GitHub reports it as Success for a required check. So any change that skips `backend` also skips the only thing that would refuse that change.
- **Failure scenario:**
  - A pull request adds `    if: github.event_name == 'push'` under `  backend:`, perhaps to save minutes.
  - On the pull request, `backend` is skipped, so the required check passes and box 3's protection allows the merge.
  - Test 24's "a job-level if" mutant passes offline, but it never runs in CI. The first time anything catches the change is the push to `main`, after the merge.
  - With `if: false`, `main`'s `backend` check stays "skipped" (which counts as green) forever.
  - The same happens with `if: false` on step 4 together with any other edit.
  - `mobile-ci.yml`'s `check` job has the same gap. QA-9 hands that trust to PL-1 explicitly (`fitlog-qa9/.../gate-wiring.mjs:5-7`, `:185`).
- **Fix:** Run each required job's guard from a different required job:
  - Make the handoff's optional request mandatory: add `node --test scripts/ci/*.test.mjs` to root `check`. This is a joint change with QA-9's `PINNED_SCRIPTS`.
  - Have the guard that runs in `backend` refuse a job-level `if`, `needs` or `continue-on-error` on `mobile-ci.yml`'s `check` job.
  - If QA-9 can't move first, an in-lane option is a small separate required workflow that runs the guard. The guard would pin that workflow too, so each of the two jobs catches a single edit to the other.
  - Add to box 1's procedure: the `backend` check run's conclusion must be `success`, not `skipped`, with the expected step lines present.

### H2. Box 2's probe stays a draft pull request, so its capture can't prove the check blocked the merge
- **Severity:** High
- **Location:** `docs/evidence/PL-1/hosted-proof-procedure.md:104-105`, `:113-116`
- **Defect:** GitHub never lets a draft pull request merge, so `merge-blocked.png` would show "Draft pull requests cannot be merged" whether or not `backend` failed or was required at all.
- **Failure scenario:** The owner follows §4 exactly. Box 2 gets recorded on a capture that says nothing about the required check.
- **Fix:**
  - Once the `backend` run has failed, mark the pull request "Ready for review".
  - Capture the merge box showing the required `backend` check failing and merging blocked.
  - Also capture `gh pr view <n> --json isDraft,mergeStateStatus,statusCheckRollup`, which should show `isDraft:false` and `mergeStateStatus:"BLOCKED"`.
  - Then close the pull request without merging. Run this only after M1's bypass setting is off.

### M1. Admin bypass is left optional, so the only person who merges may not be blocked at all

### L1. Push runs don't all reach a verdict, despite the comment and decision 6
- **Severity:** Low
- **Location:** `backend-ci.yml:11-13`; `workflow-guard.mjs:18-22`; `handoff.md:206`
- **Defect:** GitHub cancels a run that is already pending in the same concurrency group when a newer one queues, even with `cancel-in-progress: false`.
- **Failure scenario:**
  - Pushes A, B and C reach an unprotected `v2/develop`, or `main` before box 3, in quick succession.
  - B is cancelled while pending.
  - C's SQL-source check compares against its `before`, which is B. So an edit to an existing migration made in B is never compared with A.
- **Fix:** Either give each push its own group, for example `backend-${{ github.event_name == 'pull_request' && github.ref || github.sha }}`, and update `CONCURRENCY` and the tests to match, or correct the claim.

### L2. The guard's idea of a line differs from YAML's
- **Severity:** Low
- **Location:** `workflow-guard.mjs:258` (`split(/\r?\n/)`), `:81` (nested lines skipped), `:188` (step names dropped); `handoff.md:156`
- **Defect:**
  - A bare CR is a YAML line break but not a line break to the guard. Parsers that follow YAML 1.1 also break on U+0085.
  - Lines nested under the top-level `name:`, `runs-on:`, `timeout-minutes:` and the env values are skipped without being read.
- **Failure scenario:**
  - Line 2 becomes `  x\rdefaults:`, followed by `  run:` and `    shell: true {0}`.
  - The guard sees three lines nested under `name:` and passes.
  - A parser that treats CR as a line break sees a top-level `defaults.run.shell` that makes every `run:` step exit 0, including the guard's own step.
  - The handoff's reason for accepting this ("such YAML is invalid") is wrong: indented continuation lines are valid YAML.
- **Fix:** Refuse any `\r` not followed by `\n`, refuse anything outside printable ASCII plus `\n`, and refuse any meaningful line nested under a scalar. Add tests for each. This is only Low because it takes a deliberate edit, but review is the stated control and a bare CR is hard to spot in a diff.

## What held up with no finding
- **Permissions and actions:** `contents: read`, no secrets, `persist-credentials: false`, action pins identical to `mobile-ci.yml`'s, and no `${{ }}` in any `run`.
- **No shell, no leaked keys:** every command is spawned from an argument array, `supabase start`'s output is discarded, and `supabase status` is never printed.
- **Base parsing:**
  - The base must be a full 40- or 64-hex SHA; blank, all-zero, short, padded and newline-bearing values are refused.
  - It must come from a `pull_request` or `push` event (even `constructor` is refused) and match the event payload.
  - It must be in the clone, share history with HEAD, and not be HEAD.
- **`local-main`:** it only creates the branch, never moves an existing one, and refuses a tag named `main`.
- **`vendored`:** it catches `node_modules` in any letter case, including as a symbolic link.
- **Replay and summary parsing:**
  - The replay check catches missing, extra and repeated migrations.
  - The diff and lint parsers fail closed on a failed run, zero or several summaries, CRLF output, the wrong schema set and drop statements.
- **Guard key checks:** repeated keys at every level, flow style, block scalars, anchors and merge keys, quoted keys, tabs, `---` and odd indentation are all refused.
- **QA-9 compatibility holds:**
  - QA-9's pinned baseline line matches this guard's.
  - Its touched-file format check reads only JavaScript and TypeScript.
  - Its config inventory covers `apps/mobile` only.
  - `onlyBuiltDependencies` includes `supabase`, so the CLI binary installs.
