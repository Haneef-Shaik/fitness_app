## Findings, most severe first

### F1 · Medium: steps before `pnpm check` in `mobile-ci.yml` aren't held, so one edit there can still empty or redirect `check`
- **Location:**
  - The gap: `scripts/ci/workflow-guard.mjs:335-374` (`mobileStepProblems`). Line 366 only counts plain `pnpm check` steps. Lines 343-359 accept any extra `run` step, any pinned `uses` action, and any `with:` inputs, which are never compared.
  - The overclaim: `.github/workflows/ci-guard.yml:15-19`; `workflow-guard.mjs:18-25`; `handoff.md:18-20`; `checkpoint.md:27-28`; `review-0535-corrections.md:16`; `final-2026-10-27T0635Z.md:4`; the title of the test at `ci-guard.test.mjs:194` ("cannot be skipped, emptied or redirected").
- **Defect:** The guard only requires one plain `pnpm check` step. The steps before it, and the inputs of the actions it uses, are not pinned. A single edit to `mobile-ci.yml` alone can therefore make `check` pass without running anything, and both guard jobs accept it.
- **Failure scenario:**
  - Insert `      - run: npm pkg set scripts.check="echo skipped"` just before `      - run: pnpm check`.
  - The guard reports nothing (checked by reading the code; I ran no mutant):
    - no FORBIDDEN pattern matches (`:118-131`);
    - no counted name is redefined (`:149-164`);
    - `run` is an allowed key, with no `if` or `shell`;
    - there is still exactly one plain `pnpm check`.
  - Result: `check` goes green with no typecheck, lint or tests, and `backend` and `ci-guard` stay green.
  - A second variant: add `ref: <old green SHA>` under the checkout's `with:`. The job then runs old code.
  - A third: add any pinned action that exports `NODE_OPTIONS`.
  - QA-9's `gate-wiring.mjs` can't catch any of these, because it runs inside the very `pnpm check` that was replaced.
- **Fix (preferred, in-lane):**
  - Pin `mobile-ci.yml`'s steps up to and including `pnpm check` exactly, the way `STEPS` pins backend's:
    - checkout and setup-node with their exact inputs;
    - the baseline step's `shell: bash` and its run lines;
    - `pnpm/action-setup` with no `with`;
    - the install line.
  - Allow further unconditional steps only after `pnpm check`. QA-9's planned R2 step still fits.
  - Add the `npm pkg set` and `ref:` mutants to the tests.
- **Fix (fallback):** Narrow every claim listed above to what is actually held for `check`: job and step `if`, `needs`, `continue-on-error`, triggers, `defaults`, `shell` and `env`. Add "a step before `pnpm check`, or an input to its actions, can still empty or redirect it" to the residual risks.

### F2 · Low: the residual-risk list names `package.json` only, but other single-file edits also neuter the jobs
- **Location:** `handoff.md:107-108`; `review-0535-corrections.md:54-55`; `hosted-proof-procedure.md:135-137`; `workflow-guard.mjs:23-25`
- **Defect:** Every required job runs the change's own code. One edit to `.npmrc` can set pnpm's `node-options`, which becomes `NODE_OPTIONS` for both `pnpm check` and `pnpm backend:test`. One edit to the scripts or tests those commands run has the same effect. Neither is listed.
- **Failure scenario:** A pull request adds `node-options=--require ./x.cjs` to `.npmrc`, and `x.cjs` forces a zero exit. `check` and `backend` both go green. Both guards pass, since no workflow changed.
- **Fix:** State the general rule: the guard covers only workflow-file skips, and anything the jobs run or configure is trusted to review. With one maintainer, that review is the M2 decision.
