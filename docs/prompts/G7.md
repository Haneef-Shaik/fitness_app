## How, in this repo

### Q1 does not have to block the start

Build the **resolver interface first**:

```ts
interface FoodResolver {
  search(query: string): Promise<Candidate[]>;
  resolve(ref: FoodRef): Promise<Food>;
}
```

with an **internal-catalog implementation** behind it. A third-party provider then becomes *one more
implementation*, not a rewrite. This is the same shape as the existing `app/seed/catalog.py` — a
seeded internal source that works standalone.

The interface is the answer to *"can we start?"*; the provider is the answer to *"is it good?"*.

### Macros are denormalised onto `meal_items`

A food's nutrition can be corrected later, and **a logged meal must not silently change
afterwards**. This is the nutrition analogue of `target_snapshot`, and the same principle as
**AC-12/I1**: what happened is frozen; what is planned may change.

Test it directly: log a meal, edit the food's nutrition, assert the meal's macros are **byte
identical**.

### Only `confirmed = true` counts (D5)

Wire this **at the query layer, once**, so no later screen can forget it. An unconfirmed item is
visible in the UI and contributes to **no** total — not the day, not the week, not a chart, not a
preview.

### Meals reuse the outbox

Meals are offline writes too. They use `H3.2` **unchanged**. If the outbox turns out to be coupled
to sessions, fix the coupling here and record it as a G3 defect in the handoff — do not write a
second queue. Two queues is how one of them silently stops flushing.

### The day

Totals are per the **profile's local date** (**I7**), resolved the same way training does it. The
client never computes its own "today".

## Invariants you must not break

- **I2 — only `confirmed = true` nutrition counts** (D5). Enforced at the query layer in this goal.
- **I6 — canonical units in storage** (g, ml); convert at the display edge only.
- **I7 — the day is the profile's day.**
- **I8 — every write is idempotent on a client-generated key.** Meals included.
- **I9 — one response envelope, always, with a `request_id`.**
- **I13 — filtered-empty ≠ genuinely empty.** Food search with no matches offers "create it"; an
  empty diary offers "log your first meal".
- **I12 — estimated never looks like confirmed** — G8 builds the estimating, but the *schema* and
  the *display distinction* start here.

## Traps — written before you hit them

- **Joining to `foods` for analytics** instead of reading the denormalised columns. It works today
  and rewrites a user's history the first time a food is corrected.
- **Letting an unconfirmed item into a total "just for the preview".** The preview *is* the bug.
- Writing a second outbox because the first one "was for sessions".
- Storing a provider's identifier as the primary key of `foods`. Q1 may still change; the provider
  is an implementation detail behind the resolver.
- Putting a per-100 g figure and a per-serving figure in the same column. Decide, document in
  `docs/02` §4.2, and test the conversion.
