## How, in this repo

### AC-10 is the sharpest test in the project

After a user edits a quantity and confirms:

- `meal_items.confirmed = true` **and** `user_corrected = true`, carrying the **new** value
- the `food_analysis_items` row is **byte-identical to before**

**Assert byte-identity, not field equality.** Field equality passes when a field you forgot to
compare changed. Serialise the row before and after and compare the bytes.

Make the analysis tables **genuinely append-only**: no `UPDATE` statement against them anywhere in
the codebase. Add a test that greps for one if that is the most honest guard available, and a
database-level guard if one is practical.

### Containment is a hard requirement

- The **worker is a separate process**. The API never calls the model inside a request.
- The **gateway has a timeout**, a strict JSON schema, and rejects anything that does not match.
- A failed analysis **degrades H-08 to manual entry with a plain sentence** — not a retry spinner,
  not an error code.
- **Never auto-confirm above a confidence threshold** (Q7 → no, BRD §12.7). Confidence is
  information shown to the user; it is not permission.

Test containment by **killing the AI service and logging a full workout**. That test is not optional
— it is the reason this goal is allowed to exist alongside the logger.

### Estimated never looks like confirmed (I12)

Dashed border, **"Est." chip**, and **it adds nothing to any total until confirmed**. The design
system already specifies the treatment; this goal implements it.

### Uploads

Signed uploads, **EXIF stripped on the client and again on the server**. Both, because either one
alone is a single point of failure for location data in a photo of someone's kitchen.

## Invariants you must not break

- **I14 — no AI failure touches training.** The containment test is this invariant's only proof.
- **I12 — estimated never looks like confirmed**, and adds nothing to a total.
- **I2 — only `confirmed = true` nutrition counts** (D5).
- **I8 — idempotency on a client-generated key.** An analysis job submitted twice is one job.
- **I9 — one response envelope, always, with a `request_id`** — including AI failures, which is
  exactly when a user will want to quote one.

## Traps — written before you hit them

- **An `UPDATE` on an analysis row "just to fix a typo".** The append-only guarantee is worth
  nothing the first time it is bent.
- **A synchronous call to the model inside the request path.** It will be fast in testing and it
  will take the API down on a bad day.
- **Confidence used to skip confirmation.** Q7 is answered: no.
- Asserting AC-10 with field equality. It passes while something you forgot drifted.
- Stripping EXIF only on the client, where a modified client can simply not.
- A failed analysis that shows a raw error. Plain sentence, manual entry, move on.
